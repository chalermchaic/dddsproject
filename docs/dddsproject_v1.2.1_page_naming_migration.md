## 1. ปัญหาปัจจุบัน (Problem Statement)

ชื่อไฟล์หน้าจอทั้งหมดใน `pages/` มี emoji ฝังอยู่ในชื่อไฟล์โดยตรง เช่น `1_📢_Marketing.py` ทำให้เกิดปัญหา:

* URL ของแต่ละหน้ามี emoji/อักขระ unicode ปนอยู่ (ถูก percent-encode ในแถบที่อยู่เว็บ) อ่านไม่ออก คัดลอกไปวางที่อื่นลำบาก
* ชื่อไฟล์แบบนี้ไม่ใช่มาตรฐานทั่วไปของโปรเจกต์ Python (ควรเป็น ASCII + snake_case)
* เสี่ยงมีปัญหาข้ามระบบ (Windows/macOS/Linux, Git, Terminal, CI) ที่การจัดการชื่อไฟล์ unicode ไม่เหมือนกันทุกที่
* ชื่อไฟล์ที่ปรากฏในเอกสารประกอบ (`plan_2_user_manual.md`, `user_manual.docx`, `plan_4_source_code_prototype.md`) ก็ต้องพิมพ์/คัดลอก emoji ตามไปด้วยทุกครั้ง

## 3. แนวทางที่ยืนยันแล้ว — ไม่ต้องเลือก A หรือ B (แก้ตามที่ตรวจโค้ดจริงเจอ)

**ข้อเสนอเดิมของแผนนี้เข้าใจผิด:** ตอนแรกสมมติว่าระบบใช้ Streamlit multipage แบบ auto-discovery ล้วน ๆ (อ่านไอคอน/label จากชื่อไฟล์โดยตรง) จึงเสนอ 2 ทาง คือ "เปลี่ยนชื่อไฟล์อย่างเดียวแต่เสียไอคอน" กับ "ย้ายไปใช้ `st.navigation()`/`st.Page()` เพื่อไม่เสียไอคอน"

**ความจริงจากการตรวจโค้ด:** `auth.py` มีฟังก์ชัน `build_navigation()` ที่ใช้ `st.navigation()` + `st.Page()` อยู่แล้ว โดยอ่านค่าจากตัวแปร `PAGE_DEFS` — แปลว่าระบบแยก **title / icon / path ไฟล์** ออกจากกันอยู่แล้วในระดับโครงสร้าง เพียงแต่ค่า path ใน `PAGE_DEFS` ยังชี้ไปที่ชื่อไฟล์เดิมที่มี emoji อยู่ (และดูเหมือนยังไม่ได้กำหนด `url_path` แบบ ASCII ให้แต่ละหน้าไว้)

**ผลคือ:** ไม่มี "แนวทาง A vs B" อีกต่อไป เพราะยังไงก็ต้องแก้ `PAGE_DEFS` เพื่ออัปเดต path ให้ตรงชื่อไฟล์ใหม่อยู่ดี — และในเมื่อต้องแก้จุดนั้นอยู่แล้ว การเพิ่มพารามิเตอร์ `url_path` ให้แต่ละหน้าไปพร้อมกัน (เพื่อให้ URL เป็น ASCII สะอาด แทนที่จะปล่อยให้ Streamlit สร้าง slug จาก `title` ภาษาไทยเอง) แทบไม่เพิ่มงานเลย **จึงสรุปเป็นแนวทางเดียว 3 ขั้นตอน:**

1. `git mv` เปลี่ยนชื่อไฟล์ 8 ไฟล์ตามตารางข้อ 2 (รักษาประวัติ Git)
2. แก้พาธใน `PAGE_DEFS` (`auth.py`) ให้ชี้ไปที่ชื่อไฟล์ใหม่ทั้ง 8 รายการ พร้อมเพิ่มพารามิเตอร์ `url_path` แบบ ASCII ให้แต่ละหน้า เช่น:
   ```python
   PAGE_DEFS = [
       {"file": "pages/0_home.py", "title": "ภาพรวม", "icon": "🏠", "url_path": "home"},
       {"file": "pages/1_marketing.py", "title": "งานการตลาด", "icon": "📢", "url_path": "marketing"},
       {"file": "pages/2_sales_followup.py", "title": "ติดตามการขาย", "icon": "📞", "url_path": "sales-followup"},
       {"file": "pages/3_order_billing.py", "title": "ใบเสนอราคา/ชำระเงิน", "icon": "🧾", "url_path": "order-billing"},
       {"file": "pages/4_customer_profile.py", "title": "ข้อมูลลูกค้า", "icon": "👤", "url_path": "customer-profile"},
       {"file": "pages/5_support_ticket.py", "title": "รับแจ้งปัญหา", "icon": "🎫", "url_path": "support-ticket"},
       {"file": "pages/6_analytics_dashboard.py", "title": "แดชบอร์ดวิเคราะห์", "icon": "📊", "url_path": "analytics-dashboard"},
       {"file": "pages/9_portal.py", "title": "Portal ผู้สนใจ/ลูกค้า", "icon": "🌐", "url_path": "portal"},
   ]
   ```
   *(โครงสร้างจริงของ `PAGE_DEFS`/`build_navigation()` อาจต่างจากตัวอย่างนี้เล็กน้อย — ให้เปิดโค้ดจริงมาปรับ key ให้ตรง เจตนาคือ "แก้ path + เติม url_path" เท่านั้น)*
3. อัปเดต `tests/e2e/test_dfd_evidence.py` และ `VERSION` (`1.2.0` → `1.2.1`)

**ข้อดีของการที่ระบบมี `build_navigation()` อยู่แล้ว:** ไอคอนเมนูจะ**ไม่หายไปเลย**ตลอดการแก้ (เพราะ `icon` ผูกกับ `PAGE_DEFS` ไม่ใช่ชื่อไฟล์) และการกรอง RBAC ตาม Role ก็น่าจะทำอยู่แล้วในจุดที่เรียก `build_navigation()` (กรอง list ก่อนส่งเข้า `st.navigation()`) — จุดนี้เป็นจุดเสี่ยงเดียวที่ต้องระวังตอนแก้ (ดูข้อ 7.1)

## 7. วิเคราะห์ผลกระทบโดยละเอียด (Detailed Impact Analysis)

### 7.1 ผลกระทบระดับโค้ด (Code-level)

* **`auth.py` → `build_navigation()` / `PAGE_DEFS`:** จุดเสี่ยงสูงสุดของงานนี้ทั้งหมด เพราะเป็นจุดเดียวที่ผูกทั้ง path ไฟล์ + RBAC filtering (สันนิษฐานว่ามีการกรอง `PAGE_DEFS` ตาม role ก่อนส่งเข้า `st.navigation()`) ถ้าแก้ path ผิดหรือพิมพ์ตกหล่นแม้ 1 รายการ หน้านั้นจะหายไปจากเมนูของทุก Role ทันที **ควรแก้และทดสอบทีละหน้า ไม่แก้พร้อมกันทั้ง 8 หน้าแล้วค่อยเทสต์**
* **`st.switch_page(...)` ทุกจุดในโค้ด:** ถ้ามีปุ่ม "ไปหน้า X" ที่เรียกด้วย path ไฟล์ตรง ๆ (ไม่ผ่าน `PAGE_DEFS`) ต้องแก้ให้ตรงชื่อไฟล์ใหม่ทุกจุด ไม่งั้นกดแล้วขึ้น "หน้าเว็บไม่พบ"
* **`bootstrap.py`:** ตรวจว่ามีการเช็คว่าไฟล์ `pages/*.py` ครบตามชื่อที่คาดไว้หรือไม่ (ถ้ามี hardcode ชื่อไฟล์เดิมไว้เช็ค ต้องแก้ด้วย)

### 7.2 ผลกระทบระดับชุดทดสอบ (Test-level)

* **`tests/test_smoke.py`:** ชื่อไฟล์ขึ้นต้นด้วยตัวเลขและ (เดิม) มี emoji จึง `import` แบบปกติไม่ได้ — มักใช้ `importlib.util.spec_from_file_location(...)` โหลดไฟล์ด้วย path string ตรง ๆ ถ้าเป็นแบบนี้จริง **ต้องแก้ path string ทุกจุดในไฟล์ทดสอบนี้** ไม่งั้น Smoke Test import ไม่เจอไฟล์แล้ว fail ทันที
* **`tests/test_dfd_flows.py`:** ตรวจว่ามีการอ้างอิง path/URL ของหน้าจอในการจำลอง Flow หรือไม่
* **`tests/e2e/test_dfd_evidence.py`:** ใช้ Playwright เปิดหน้าเว็บจริงตาม URL — ต้องเปลี่ยน URL ทุกจุดที่อ้างอิงเป็น `url_path` ใหม่ (เช่น `/marketing` แทน URL เดิมที่มาจาก title/emoji) เป็นไฟล์ที่กระทบหนักสุดในชุดทดสอบเพราะจำลองพฤติกรรมผู้ใช้จริงทั้งหมด
* **`build_report.py`:** เช็คว่ามีอ้างอิงชื่อไฟล์ภาพ/หน้าจอเดิมหรือไม่

### 7.3 ผลกระทบระดับ Git และการดีพลอย (Git & Deployment)

* ใช้ `git mv` แทนการลบ-สร้างไฟล์ใหม่ เพื่อรักษาประวัติ commit เดิมของแต่ละหน้า
* ทำงานนี้ในสาขาแยก (feature branch) ก่อน merge เข้า main
* ตรวจ `Dockerfile`/`docker-compose.yml`/`Makefile` ว่ามีจุดใดอ้างอิงชื่อไฟล์เดิมแบบเจาะจงหรือไม่ (ปกติ copy ทั้งโฟลเดอร์ `pages/` จึงไม่น่ากระทบ แต่ควรเช็คให้ชัวร์)

### 7.4 ลำดับการทำงานที่แนะนำ เพื่อไม่ต้องทำซ้ำสองรอบ

1. ทำ Migration ชื่อไฟล์/URL ตามแผนนี้ให้เสร็จและทดสอบผ่านทั้งหมดก่อน (ข้อ 4-5)

3. สุดท้ายค่อยอัปเดตเอกสาร (plan_2, plan_4, user_manual.docx) ให้ตรงกับทั้งชื่อไฟล์ใหม่และภาพชุดใหม่พร้อมกันในรอบเดียว

### 7.5 แผนสำรองหากมีปัญหากลางทาง (Rollback Plan)

* ถ้า RBAC พังหลังแก้ (เมนูโผล่ผิด Role หรือหายไปทั้งหมด) ให้ `git revert` กลับไปที่ tag `v1.2.0` ทันที แล้วไล่แก้ทีละไฟล์แทนการแก้พร้อมกันทั้ง 8 ไฟล์
